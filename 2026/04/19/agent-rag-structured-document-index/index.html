用标题树和原文定位改进长文档检索

2026-04-19 Agent

知识库里出现一句「超限时应暂停处理」，单独看这一段，很难知道它说的是哪项业务、适用哪个版本。对于有清晰章节的手册，我会把文档结构保留下来，让检索片段带着可追溯的上下文。

先做一层轻量索引

给每个片段存标题路径、文档版本、父章节 ID、页码或原文偏移。索引词可以包含章节名和一段短说明，展示证据时仍读取原文。查到叶子片段后，需要完整条件时再展开父章节或邻近段落。表格中的数值也应连同表头、单位和脚注一起呈现。

复杂问题可以拆成几次检索，例如分别找「提交条件」和「例外条件」。运行时要记录已经查过的主题及剩余检索预算，避免围着同一批片段反复搜索。

文档入库时把段落、表格和证据位置一起保存

例如新版「报表运维手册 / 第三章 / 失败处理 / 补跑条件」下有一张表。表头按任务类型给出允许补跑的时限，脚注还限定了跨月任务。索引记录可以包含 doc_id、revision、section_path、parent_id、page_from 和 page_to。把「任务类型、时限、跨月例外」写进用于匹配的文本，引用仍指向原表和脚注。

索引文字与展示证据可以各有一份。给索引附上一句章节简介能提高匹配几率，展示时则把原段落取回来。若上下文只够放几百字，先保留命中的条件、例外和行列标题。父章节很长时，用页码或锚点获取邻近范围，避免整章展开后挤掉其他有关资料。

版本更新要能解释命中了哪个批次

我会按文档版本写入整套新片段，索引完成后切换该版本为当前版。旧版仍可通过明确的历史查询访问。若新批次只写了一半，默认问答仍使用完整旧批次。这样发布期间就不会同一答案引用两种版本的表格。

对于包含两个问题的查询，例如某种任务何时可补跑、跨月时又怎么办，可以检索两次，分别带上章节线索。第二次只补尚缺的例外条件，并把版本锁在同一份手册。实验时给每个预期引用定到页，分别记录版本准确率、关键条件完整度和每题展开的字符量，观察结构化索引增加的上下文是否真的有帮助。

用容易串版本的案例验证

我会放入同标题、不同年份的两份手册，再问一个只在新版修改过的限制。检查是否命中正确版本、能否展开足够的限定条件，以及引用是否回到正确页。只有样本显示跨实体关联经常缺证据时，才值得进一步考虑知识图谱等更重的结构。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§3.3。
