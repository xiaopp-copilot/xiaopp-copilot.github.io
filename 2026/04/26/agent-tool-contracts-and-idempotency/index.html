给 Agent 工具设计清晰的参数、错误和重试语义

2026-04-26 Agent

一个「为草稿添加标签」的工具，描述至少要说清对象类型、支持的标签和成功后返回什么。我会用 JSON Schema 限制参数形态，让执行端再检验草稿存在性、当前权限和业务状态。结构正确只能证明数据满足接口格式，真正是否能执行还要由业务系统决定。

工具应返回可处理的结果

成功时返回草稿 ID、写入后的标签和必要版本信息。参数错误返回错误字段及允许值，权限不足直接结束该路径，短暂服务繁忙才允许在预算内重试。网络超时有时意味着远端已经写入，所以修改接口宜支持幂等键，或提供按请求 ID 查询结果的能力。

工具边界可以沿读写划分。查询草稿与修改草稿使用独立权限，写入要求按动作确认。能用同一个查询工具表示的相似筛选就合在一起，避免工具列表堆出一批只差一个参数的方法。

把参数约束写进实际契约

如下是添加标签工具的一段 JSON Schema 示例。模型比较容易从枚举里选出合法标签，应用还需要核对该草稿是否属于本次可访问的空间。

我会让运行时从操作记录生成幂等键，所以模型的 schema 里无需填它。写操作受理后保存请求键、目标草稿和参数指纹。相同键重放时，参数一致就返回原结果。参数差异表示调用发生了冲突，应让调用方用新的操作标识提交。

超时后的恢复方式由业务状态决定

如果标签更新和幂等记录在同一个服务、同一个数据库里，可以事务写入两者。工具若依赖远程服务，则要看服务端是否接受幂等键，或者能否按请求标识核对不确定结果。举例来说，看到「连接已关闭」不足以判断服务处理到了哪一步。此时返回 OUTCOME_UNKNOWN，再由运行时确认当前标签状态或原请求状态。

工具契约还可以约定失败时下一步需要什么信息。无权限时只返回必要原因，避免暴露目标资源细节。字段校验失败时给出允许值，调用方可以修正。服务繁忙时保留重试提示和预算约束。在日志中关联同一操作的多次尝试，便于复盘为什么用户只看到一次结果、系统却发出了两次请求。

我的联调样本

依次测试错误标签、无权限、正常写入和写入成功但客户端超时。最后一个场景要核对重复请求没有生成第二次写入，同时能查到第一次的结果。测试过这些路径，模型遇到错误时才有信息决定下一步。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§4.1–4.2、§4.5。
