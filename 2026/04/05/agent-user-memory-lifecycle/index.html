让 Agent 的用户记忆可以纠正、隔离和删除

2026-04-05 Agent

用户说「这次用英文写」，与「以后我的周报都用英文」表达了不同的范围。我会把会话要求留在当前任务，把明确的长期偏好写成一条可更新的记录，并保存用户、适用范围、证据和更新时间。这样未来遇到新要求，可以定位到该修改哪一条。

写入和读取分别做判断

写入时先把候选条目分类成事实、长期偏好或当前要求。只存对后续任务有价值、来源明确的条目，避免把模型推断和文档里的文字当成用户确认。读取时先按账号和工作空间筛选，再根据任务挑选少量相关记忆。保留结构化值和来源，用户才能追问系统为什么用了某条偏好。

记忆记录要带上作用域和版本

我会把偏好存成 (user_id, workspace_id, preference_key) 下的一条有效记录。每条另有 value、revision、source_message_id 和 updated_at。例如 weekly_report.language=zh-CN 只适用于周报。收到「所有交付都改成英文」这类更宽的要求时，还应保留独立的适用范围，由明确的覆盖规则决定它和某项任务的特定设置如何叠加。

预测偏好和用户确认的偏好应有不同来源类型。如果用户近三次都选了英文，可以生成候选记录，但候选需要独立存放，读取时避免当成长期确定设置。应用拿到本轮明确要求后，应先执行它，再决定是否要更新长期记录。这样一次例外不会影响以后所有任务。

修改、删除和跨设备读取怎么实现

同一条设置可能在两台设备上同时更新。我会让写入带预期的 revision，冲突时先读取最新记录，再决定能否重新应用本轮指令。用于读取的向量索引和缓存可以异步更新，查询返回前仍应通过主存储校验来源、状态与作用域。旧索引即使尚未来得及更新，也只能提供候选。

删除时可以先让主记录变为不可读，再清理缓存和索引。允许重试的后台任务按记录 ID 和版本执行。这样用户删除又重新添加同名偏好时，旧版本的延迟清理不会删掉新记录。对这类多副本系统，我最关注的是用户发出纠正后，下一次读取能否立即看到已经生效的版本。

测一下改口和删除

我会构造四轮对话。用户先设定周报语言，随后只对一次周报临时换语言，再修改长期偏好，最后要求删除。分别验证临时要求结束后长期偏好能恢复、明确纠正能覆盖旧值、删除后索引与缓存也不会继续命中。用另一账号跑相同问题，可以顺手验证隔离边界。

我的取舍是先做少量、可解释的记忆。等验证了纠正与删除，再扩大可保存的类型。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§3.1。
