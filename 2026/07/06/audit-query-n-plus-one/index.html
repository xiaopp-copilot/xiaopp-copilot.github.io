消除三处 N+1，把稽核查询从 2.81 秒降到 580 毫秒

2026-07-06 实习

查询稽核点关联制度文件时，耗时分散在三处逐项调用里，包括一次远程 RPC 路径和两处本地数据库路径。我沿着响应组装逐项核对数据来源，将能批量取得的数据提前加载，再用请求内的 Map 按 ID 索引。笔记记录的同一接口平均耗时从 2.81 秒降到 580 毫秒，降幅约 79%。

批量化时保留原有语义

原单条查询会取回未删除的记录，后续由业务层处理启停条件。已有批量接口会先筛去未启用的数据，直接替换会让这些记录消失。我新增了包含未启用状态的批量查询，沿用原来的删除过滤和业务判断。

外部 SDK 的远程调用无法直接改造，我评估了按单个 ID 缓存、TTL 为 5 分钟的 Redis 方案。它让不同请求可以复用相同记录，也避免为每种 ID 组合创建缓存键。排查过程中遇到 Jackson 无法处理 LocalDateTime 的问题，通过注册 JavaTimeModule 并使用 ISO-8601 字符串解决。SDK 已内置缓存，这一层 Redis 是否保留需要结合命中情况和维护成本再判断。

同日还处理了两个补全人员信息接口。一个按实际查询条件增加复合索引，将机构维度放在首列。另一个给按用户 ID 的查询增加 Redis 缓存。

我的思考

我会先数清循环里每种 I/O 的调用次数，同时写下旧查询的过滤条件。前者决定优化能省掉多少工作，后者决定加速后能否返回相同业务结果。请求内的索引可以随请求释放。跨请求缓存则需要另外考虑数据新鲜度和冷缓存行为，复盘时也应将两者的收益分开验证。
