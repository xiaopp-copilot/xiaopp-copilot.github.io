搭语音 Agent 时，先量延迟和打断恢复

2026-06-28 Agent

做语音问答原型时，可以先用语音活动检测、语音识别、语言模型和语音合成组成级联链路。我会记录用户停止说话、识别结果可用、模型开始输出、音频开始播放这几个时点。这样能看到延迟来自等停顿、等模型，还是音频合成和播放队列。

流式处理与打断

识别可以逐步返回文本，稳定片段进入下一阶段，模型生成的完整短句可交给 TTS。用户在播放时开口，新轮次应能让旧轮次停止生成，清掉仍在排队的旧音频，并在会话状态里保留用户实际听到的部分。后端工具若已经启动，则根据工具是否可取消来处理，并按轮次隔离晚到的结果。

先约定时钟和可测的端到端指标

用同一时钟记录一套事件。假设在一轮样例中，用户最后一个音频帧在 1000 毫秒到达，VAD 在 1300 毫秒判定结束，ASR 在 1380 毫秒给出可用文字，第一段合成音频在 1640 毫秒开始播放。用户实际感知的首段响应延迟是 640 毫秒，300 毫秒花在等停顿结束。若 ASR、模型和 TTS 已流式并行，各自耗时会重叠，分析时要看完整时间线。

服务端记录最早合成到哪一帧，客户端记录第一帧真正开始播放。两者之间若差别很大，可以继续检查网络传输、音频缓冲和设备调度。跨客户端和服务端比较时间时，优先用各自的单调时钟计算阶段耗时，或明确校准方式。性能统计至少按网络条件、设备和轮次类型拆开，避免平均值把差异盖住。

用户打断时区分正在播放和后台工作

给每次输出带一个 turn_id。检测到用户开口时，播放器先停止并清理该轮剩余音频，生成端也收到取消信号。下一轮上下文只保留客户端确认已播放的文本范围，以及仍有价值的后台状态。无法及时中止的后台结果仍按旧轮次接收，再根据新问题决定要不要使用。

用户说「等一下，我问的是上周」时，旧查询即使率先完成，也应避免自动播报。测试时记录用户开口的时间、停止播放的时间和切换后的新答案。对语音任务而言，打断能否顺畅恢复和首包是否快，值得分别验收。

我会如何验证

用短问句、自然停顿、长问题和播到一半打断几种场景，记录从用户停说到第一段可听音频的时间，也记录开始打断到旧音频停下的时间。听一遍录制结果，核对系统有没有把思考时的停顿误当句末。只有这组基线测清楚，才好判断是否需要更紧耦合的音频架构。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§9.2–9.6。
