用 Trace 定位 Agent 失败发生在哪一步

2026-06-14 Agent

知识库助手回答错了，可能是资料没被索引、检索漏了依据、模型忽略了证据，或者结果校验没执行。我会用一个 Trace ID 串起任务，并把每次模型请求、检索、工具调用与结果校验记成有父子关系的 span。

运行记录里保留什么

模型 span 记录版本、时间和用量，检索 span 记录查询意图和候选资料 ID，工具 span 记录类型、参数校验结果、耗时和错误类别。最终 span 记录任务是否满足验收条件。含隐私的正文和参数可以保留脱敏摘要或受控引用，让调试能定位到具体路径，也便于限制原文的访问和保留期限。

看一条有并行分支的 Trace

下表是一条演示轨迹。时间从任务开始算起，两个读取操作并行，生成阶段等待两边结果到齐。

过程 开始 结束 观察
解析用户问题 0 ms 260 ms 识别出手册版本 v2
文档检索 260 ms 470 ms 两条候选都来自 v1
版本元数据查询 260 ms 800 ms 确认 v2 已发布
生成回答 800 ms 1110 ms 引用了 v1 的限制
结果校验 1110 ms 1180 ms 发现引用版本不一致

表里可以读出两件事。质量问题出现在检索返回了错误版本，结果校验才拦住。时间上，这两条并行读取一共占 540 毫秒的等待，较慢的元数据查询决定了什么时候可以开始生成。把两条 span 的耗时直接相加，会高估它们对用户等待的影响。

为每类问题保留能触发回归的记录

我会先检查 v2 有无进入索引、索引版本何时切换、检索是否拿到了明确的版本参数。若 v2 已可检索却未命中，可以重放精简过的查询和索引快照。然后保存「问题、预期版本、关联候选 ID」作为回归材料。集成环境中还要把检索、工具和评估记录的 Trace ID 对齐，避免事件异步到达时被串到下一轮。

线上指标可以按错误原因、任务类型和版本聚合。只看全局均值，容易漏掉特定长任务的抖动。也应区分「系统检测到错误」「向用户发出部分结果」和「成功交付」三种结果，便于判断局部失败是否真的影响交付。

从一条失败记录提出下一步

例如用户问新版接口的限制，回答引用了旧版。先查新版是否出现在检索候选，再查候选是否进入模型输入。新版从未进入候选，就先测版本过滤与召回。新版有依据但回答引用了旧版，就检查资料排序和生成约束。我会为定位到的原因保存一个回归用例，改动一项后重放同类样本，看看失败是减少了，还是转移到了下一步。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§6.8–6.10。
