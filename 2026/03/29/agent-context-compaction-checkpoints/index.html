长任务压缩上下文时，怎样保住进度和证据

2026-03-29 Agent

让一个 Agent 连续核对几十份文档，最长的消息通常是工具返回的原文。窗口接近上限时，我会保留最近几轮的具体操作，把较早的内容归纳成可恢复的检查点。检查点里最重要的是后续工作还要依赖的状态。

压缩时保留什么

  • 用户目标、已经确认的约束、完成条件和明确排除项。
  • 已完成和待处理的对象、关键决定及理由、失败后尝试过的方法。
  • 可重新读取的证据位置，例如文档 ID、章节、文件路径或查询结果 ID。
  • 在运行时单独保存的进行中工具调用及其 ID。压缩历史时保持调用和结果配对。

长任务可以另外附上一小段运行时状态，记录剩余预算和正在执行的任务。状态应来自实际工具和任务记录。压缩优先移除可回查的冗长结果，并给下一次响应留出空间。

在真的超窗之前做一次检查点

应用每轮组装完准备发送的消息后，先估算输入 token，同时留出模型输出空间与可能追加的工具结果。对于一个假设的 32k 窗口，可以给输出预留 4k，再留一段缓冲，超过剩余预算时才压缩。具体数字从任务中常见的请求体量反推。较短的检索结果可以继续保留，重复日志和已存档附件优先缩短。

摘要与任务状态用不同来源

压缩模型负责归纳文本，已提交的工具调用、是否经过用户确认以及剩余预算仍由运行时提供。若摘要写了「备份已处理」，任务表却显示扫描仍在运行，恢复时应以任务表为准。摘要也要注明覆盖的起止轮次，便于将后面没有压缩的消息连在后面，避免遗漏用户新补的限制。

我的测试会安排一次中途纠正。例如处理到一半，用户要求忽略早于第三版的文件。压缩后复跑还要验证这条修改仍生效，且已完成、未完成集合都有正确的版本边界。当较旧的证据只剩引用时，测试应实际走一次回查，确认该引用还能定位原文。

如何验收压缩

我会在同一批任务中比较压缩前后能否继续处理剩余文档、正确引用较早的证据，并延续用户曾纠正过的约束。摘要变短只能说明减少了 token。压缩后可以准确继续，才说明保住了任务需要的信息。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§2.6–2.7。
