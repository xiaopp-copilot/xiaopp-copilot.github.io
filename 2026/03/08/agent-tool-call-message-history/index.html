把工具调用和结果正确写回 Agent 的消息历史

2026-03-08 Agent

模型一次请求「查工单状态」与「查最近变更」，两个工具很可能以不同顺序完成。如果只把返回文本依次拼起来，下一轮容易把一条结果归到错误的调用。运行时应保存模型那条调用消息，并用调用 ID 将每条结构化结果关联回去。

怎样记录一轮调用

  1. 持久化该轮模型返回的工具名、参数和调用 ID。模型的自然语言回复也按消息协议保留。
  2. 校验参数和权限。互不依赖的只读查询可以并行执行，有前后依赖的调用等前置结果完成。
  3. 每个调用都记录一个终态结果，包含成功数据或可分类的错误。以调用 ID 配对，把整轮结果按所用接口的消息格式交给模型。

如果接口由应用管理历史，下一轮就带上完整的有效消息序列。工具返回的网页、日志和文档属于数据，里面出现的文字指令也按数据处理。

存一份能还原消息协议的执行记录

下面是应用侧的记录结构示意。不同模型接口的字段可以由适配器转换。应用至少要能恢复调用的原始顺序、参数、关联 ID 以及最终结果。

如果 c2 先结束，应用可以立刻把结果写入任务表。向模型发送下一轮时，再按协议将两个调用结果拼入历史。同轮部分失败也要回填。上面的例子足够支持「工单仍在审核」，同时应说明暂未取得变更记录，不能据此推断何时进入审核。

恢复任务时先核对调用表

工具结果写入前崩溃和工具执行前崩溃，在会话历史里看起来都像缺一条结果。我会给每个调用留下 pending、running 和终态，并保存外部请求标识。恢复后，已结束的结果直接重放，尚未启动的调用可以提交。如果调用已发出但终态不明，只读操作可以在预算内重跑，写操作先查外部状态或沿用原幂等键。

并行调用只接受互不依赖的参数。例如需要先查工单所属项目才能查询变更时，第二个查询应放到下一轮，或者由运行时在依赖完成后才调度。有些模型接口对调用消息和结果消息的相邻关系也有约束，序列化前可统一检查 ID 是否全部配对。这样历史异常能在应用侧暴露，定位时无需猜测模型看到的上下文。

我会怎么测

让状态查询慢半秒，变更查询立即返回，再反过来跑一次。两次回答都应使用正确的证据。然后在一条调用完成后中断进程，恢复时检查已完成的调用能被识别，缺失的结果有明确处理路径。这样才能把「调用过」与「已获得结果」区分开来。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§2.1–2.2。
