把 Agent 的上下文排成能复用的稳定前缀

2026-03-15 Agent

一个多轮 Agent 往往会重复发送系统规则、工具定义和历史消息。上游支持前缀缓存时，相同前缀的计算有机会复用。我会先检查应用是否把当前时间、请求编号和随机顺序的配置放进了规则开头。这些数据每轮都变化，容易缩短后续可复用的前缀。

一个可实施的排列

将有版本的系统规则和稳定的工具定义放在前面。用户消息、临时检索片段与工具结果按任务推进追加。动态状态只在需要时进入上下文，并遵守所用消息协议。工具列表如果来自多个模块，也要固定序列化顺序。规则确实更新时切换版本，缓存自然重新积累。

先找到每轮前缀从哪里开始变化

我会把请求拆成几个可记录的段，例如 policy:v3、tool_catalog:v8、历史消息和本轮补充数据。值班助手的当前时间随轮次变化，但「时间按用户时区解释」这条原则长期稳定。把时间戳放到轮次信息里，规则段就可以连续复用。工具描述从服务注册表读取时，应固定名称和排序，避免仅因数据库返回顺序变化就改了请求内容。

诊断时可以为稳定段计算指纹，并按段统计 token。若第 3 轮突然少了大量缓存命中，先看是前缀内容变了、模型切换了，还是缓存因服务端策略已过期。缓存通常依赖模型和服务的具体实现。可以让运行时记录实际返回的用量字段，并在缺失时将该项标成不可观测。

用同样的任务对照缓存的数据

先取一段固定的六轮对话，包含相同的工具结果和最后回答要求。A 组在系统规则开头拼每轮时间，B 组在本轮输入中补时间。分别测量第 1 轮冷请求和第 2 至 6 轮，记录每轮总输入 token 与缓存命中 token。整组命中比例可以用「命中 token 之和 ÷ 输入 token 之和」计算。首 token 延迟和任务总耗时可列出中位数，样本足够多时再比较 P95。

如果 B 组首 token 明显更快，端到端却变化很小，就检查工具耗时是否占了主要部分。如果命中提升但平均输入同步变长，要核算总费用和有用上下文比例。检索结果过长时，仍应按普通任务预算裁剪，并保留可回查的位置。两类优化可以在不同实验轮次评估，便于看清各自影响。

用两组请求验证

我会用同一批任务分别跑「时间放在规则前部」和「时间随本轮状态追加」两组，固定模型、输出限制和请求并发，分别观察冷启动和重复请求。记录首 token 延迟、输入与缓存命中 token、每次任务的总成本。服务不提供命中统计时，可以报告延迟差异，并把缓存归因留作待验证假设。

我更关注整项任务的耗时。为提高命中率而持续携带已经无关的大段资料，会增加上下文负担。稳定前缀与按需补充可以一起做。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§2.3。
