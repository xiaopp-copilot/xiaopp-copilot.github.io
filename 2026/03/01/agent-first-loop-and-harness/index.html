从一个工具调用循环搭起最小 Agent

2026-03-01 Agent

做一个能回答「这张工单现在卡在哪一步」的助手，可以先接两个只读工具，一个取工单状态，一个取最近的状态变更。用户用自然语言指出工单，模型选择工具并给出参数，运行时执行，模型再根据返回数据组织结论。这个循环有了真实的输入和输出，才值得扩展到更复杂的流程。

运行时负责哪些决定

我会把一次任务做成「请求模型 → 校验并执行工具 → 回填结果 → 决定是否继续」的循环。最终回答里的工单状态应能回到具体的工具结果。运行时管理工具白名单、参数、最大轮数和超时。固定的业务步骤可以写成代码节点，例如先校验当前用户有权访问工单，再允许读取详情。读取哪些已授权的字段可以交给模型决定。

把模型回合写成一段可追踪的代码

设想输入是「TK-42 卡了多久」。read_ticket 返回工单状态和最后变更时间，list_status_changes 返回一组事件。运行时还要记录本次查询的参考时间，否则「卡了多久」会随着模型采用的时间基准变化。可以先用如下伪代码表达循环，run_checked 负责校验、授权和执行。

validate_answer 可以先从可检查的字段做起。让模型在内部输出 ticket_id、status、changed_at 和 evidence_ids，再由程序核对工单号和状态是否出现在已授权的返回结果中。剩下的描述仍可用自然语言。若最近一次变更的时间查不到，回答可以给出已确认的状态，并指出时长尚无法计算。

先定几条运行时的退出规则

我会给单次工具和整项任务分别设截止时间。假设单个查询允许两秒，整个任务只剩一秒，就按更早的时间停止等待。最大轮数用来防止反复向模型请求，工具次数另计，避免一次模型回合排出几十个调用。若两轮都查询同一工单且结果版本一致，可以在返回中加入「同一结果已查询」的信号，给模型机会收束。

还要为「无数据」「权限不足」「临时失败」提供可区分的结果。前两类应告诉模型缺少什么，并避免反复原样调用。临时失败可以根据剩余预算重试一次。把这些分支交给运行时后，模型专注于决定再查哪条信息、怎样组织已经证实的事实。

第一个版本怎么验收

  • 给一张已结束的工单，检查回答能指出最后一次状态变化和发生时间。
  • 给一个不存在的工单号，检查系统如实返回查无结果，并保留可读的失败原因。
  • 模拟工具超时和模型重复调用，确认任务能在预算内停止，并告诉用户目前确认了什么。

我的取舍是先做一个有明确终点的只读闭环。新增能力时，先问业务系统能提供什么证据验证完成，再决定把多少决策权交给模型。
