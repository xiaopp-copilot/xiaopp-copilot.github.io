从一组有明确通过条件的 Agent 评估开始

2026-05-31 Agent

如果要评估一个知识库助手，我会为每个任务保存输入、资料版本、应引用的证据和通过条件。例如问「离线报表是否能补跑」，测试要同时检查引用的章节、适用条件和遗漏信息。资料没有依据时，如实说明也算通过。

通过条件要尽量可执行

先用程序检查必填字段、引用地址、数据库终态或输出文件。难以写成规则的部分，例如解释是否覆盖关键条件，可以用人工标准或模型打分，并先与人工标注对齐。任务集要覆盖正常请求、输入不完整、工具失败和无权限等情况。每次运行重置初始状态，尽量避免前一次结果影响本次。

给每个任务一份可读的测试描述

以报表补跑为例，单个用例可以先写成下面这种记录。任务环境和证据版本都有固定标识。同一用例重跑时，系统按这份描述加载相同材料。

评估程序先核对结果结构、触发过的工具和引用 ID，再检查回答是否讲对了适用条件。需要评审文字质量时，把评分规则写清。例如缺少条件算事实不完整，引用格式问题另计。对于用模型评分的部分，可以抽几条一致和不一致样本人工复核，排序不同答案时打乱呈现顺序。

失败分类能决定下一步先修哪里

记录每个任务的最终结果，也保存一个主要失败原因。检索漏召回可以修索引，工具参数错误优先看接口描述，流程正确但结论不全则检查上下文和答案约束。有些任务应查最终状态，例如操作结束后队列里只有一条对应记录。检查调用过哪些工具能帮助定位，但验收尽量围绕最终产物和业务状态。

我会给回归集增加总体和分组两种视图。总体小幅上升时，仍要看重要用例有没有退步。重要的无权限和外部写入用例可以拥有独立通过条件。样本集按版本维护，把新增失败样本和用于日常调试的样本区分开，减少反复调同几道题带来的高估。

一次通过和反复通过分开看

对于随机性较大的任务，多次运行允许区分「至少一次成功」和「每次都成功」。前者能探索能力上限，后者更接近稳定性要求。我的做法是把单次通过率、失败类型和复跑表现一起记录。修复某类失败后，将可复现样本加入回归集，再跑一遍原有样本。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§6.1–6.5。
