把耗时工具改造成可取消的异步任务

2026-05-10 Agent

一份大型报表要生成几十秒，用户中途可能问进度，也可能更改筛选条件。我会让工具启动任务后马上返回 job_id 和当前状态，后台工作进程继续生成。任务完成、失败或取消时再发事件，运行时据此恢复会话或更新界面。

把状态转换写进运行时

每个任务保存所属会话、输入版本、状态和结果引用。完成事件带任务 ID 与唯一事件 ID，消费者据此去重。收到取消请求时先记录取消意图，由工作进程确认能否终止。若用户已改了条件，旧任务晚到的结果仍可供查看，但要按版本隔离，避免覆盖当前输出。

事件也需要不同的处理方式。用户明确取消当前工作可以优先处理，普通进度可以合并，完全独立的只读任务可以并行。涉及外部写入的工作应留下可查询的状态，以便在重启时确认此前做到哪一步。

用一张状态表约束并发

我会把任务状态的更新集中到一个位置，并让每次更新携带期望的旧状态或版本。下面是一个报表任务的状态模型示意。

事件 允许的当前状态 结果
工作进程取得任务 queued running
用户取消尚未启动的任务 queued cancelled
用户请求取消 running cancel_requested，记录原因
工作进程确认停止 cancel_requested cancelled
产物已经提交 running 或 cancel_requested succeeded，保存结果引用
发生无法恢复的错误 running 或 cancel_requested failed，保存错误类别

如果进程已经提交产物，界面应如实显示完成，同时说明取消请求到达时结果已经生成。若产物只写到临时位置，可以在确认取消后清理。对修改外部状态的任务，还要记录该动作能否撤销，以便给用户准确的状态说明。

处理事件丢失和晚到结果

假设工作进程已经写好报表，刚准备发完成事件就重启。可以在同一个数据库事务中提交任务终态和待发送事件，再由独立进程投递。消费者按事件 ID 去重，界面刷新时也能直接查任务表补齐状态。这样通知渠道暂时中断，任务完成记录仍然可查。

更换筛选条件时给会话递增一个查询版本。旧报表随后完成，可以保留在自己的任务历史中。主会话只有在结果版本与当前查询一致时才展示该结果。我会用这条规则验收取消和恢复，因为用户最容易感知的问题是新请求已经发出，页面却突然回到旧报表。

我会模拟的三种时序

重复投递同一个完成事件、取消时结果恰好返回、任务执行中服务重启。三种情况都应能得到明确终态。验收既要看 Agent 的回复，也要查任务表和最终产物，确认没有发生重复展示或错误覆盖。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§4.7。
