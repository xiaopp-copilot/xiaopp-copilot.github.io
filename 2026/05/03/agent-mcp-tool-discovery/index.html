MCP 工具越来越多时，怎样做按需发现

2026-05-03 Agent

多个 MCP 服务接入后，工具列表容易出现相近的名字。例如知识库、项目文档和工单都能搜索，模型得先知道该去哪一处查。我的做法是给应用一个轻量目录，包含服务来源、工具用途、适用对象以及读写类型，再按任务选出少量候选。

发现和执行各自做什么

发现阶段先根据任务和可访问资源过滤，再向模型提供候选工具的名称、用途和来源。确认使用某项能力后，才加载完整的参数 Schema 和必要示例。执行前仍要检查当前用户的资源权限，工具的 service + name 身份也应可追踪，防止名字相同的能力被混用。目录里的来源描述属于检索信息，授权由应用和服务端核验。

目录里保存用途，也保存执行身份

我会把目录项约定成以下字段。模型只需看到帮助它选择的几个字段，实际连接信息留在运行时。

字段 示例 用途
qualified_name docs.search 区分来自不同服务的同名能力
summary 搜索授权项目中的手册 匹配用户意图
resources 文档空间 做候选范围过滤
access read 区分查询和写入动作
schema_version v3 执行前检查描述是否仍有效

当用户问「找这个项目的部署手册」，先根据项目和账号权限过滤，再按用途找文档检索。排序第一的工具如果还有歧义，可以带上备选项的来源，让模型补一个明确选择。工具定义在真正调用前读取并校验。已加载的定义可以按服务身份和版本短期复用，同名工具重连后要核对是否仍是同一个来源。

对工具发现链路设三种回退

某项工具不可达时，先区分连接故障、当前权限和工具变更。连接故障可以限次重连，版本不匹配可重新读取描述，权限不足则应该返回可用范围。几个服务名字接近时，我会把自动替换限制在明确配置的等价能力，避免文档工具失败后把内容查询发给无关的系统。

评估时也要把「候选里面有没有」和「最终调用对不对」分开。若正确工具频繁排在前 K 之外，就调整目录词和筛选。若候选已有而模型选错，则检查描述是否明确说明输入、输出和适用资源。工具多起来后，还可以比较目录动态加载次数与请求输入长度，看它节省的上下文是否抵过新增查找开销。

怎么知道工具选对了

用「查某项目手册」和「查某个工单的历史」做对照样本，再加一个同名项目、跨空间权限不同的场景。记录候选是否含正确工具、最终调用是否正确、为选择多花了多少时间。我的取舍是先用固定目录或简单筛选，当工具增长后再做更细的检索，并继续保留同一组回归样本。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§4.3、§4.8。
