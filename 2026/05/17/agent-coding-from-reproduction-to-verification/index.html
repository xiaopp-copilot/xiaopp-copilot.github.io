Coding Agent 修 Bug 时，怎样从复现走到验证

2026-05-17 Agent

给 Coding Agent 一个「含空列的 CSV 导入失败」的问题，我会先提供触发样本、入口和预期行为。Agent 应从项目的现有读入逻辑出发，跑一个能区分旧行为和期望结果的样本，再定位最小修改范围。

每一步留下可复核的证据

  1. 检查工作区约束与已有改动，读取入口、相关模块及现有测试。
  2. 过一遍含空列的输入，记录失败位置，确定是解析、校验还是保存出错。
  3. 修改产生问题的路径，复跑样本和相关测试，再查看差异有无无关变更。
  4. 交付时列出改动和实际跑过的命令，区分已验证行为与仍缺少的环境条件。

运行时可以按失败原因提供不同恢复路径。临时网络错误可以在预算内重试。参数无效要改输入。依赖缺失时，可转向现有的局部检查并保留限制。连续出现同一错误时，应停下来重新定位。

用相邻的输入猜测故障位置

一个尾部空列的最小样本可以是下表。末尾逗号表示 note 已存在但值为空。可对比一条实际缺列的记录，确认系统能区分这两种情况。

先让 Agent 在正式导入入口跑这份输入，核对三处证据。解析阶段检查字段是否按列名取得，校验阶段检查必填字段和可选字段的区别，持久化阶段检查记录是否落库以及空值使用的表示方式。假设解析已经保留了空列，校验却把所有空字符串都当错误，就把修复放在可选字段的校验逻辑上。若项目定义缺列也可补默认值，测试应按既有规则写清预期。

验证最小修改还能覆盖哪些真实数据

我会保留原始复现，并加入一个没有空列的正常输入，以及一个必填金额为空的错误输入。前者保护旧调用方，后者防止修复顺手放宽必要校验。如果导入支持带逗号的引号字段和换行，也应复用已有的覆盖，检查修改有没有误伤 CSV 的语法。

交付说明可以保存「复现命令、失败位置、修复点、验证命令」四项。如果集成测试缺少数据库，就标明该项未运行，并列出已取得的局部证据。接手的维护者可以照着复现同一输入，看到相同的失败和修复结果。

我的验收标准

同一个普通 CSV 和带空列的 CSV 都经过正常入口，只有后者的错误行为被修正。测试通过之后还要看差异是否尊重已有改动。能解释「改在哪里、用什么证据确认」，比只收到一句「已修复」更方便交接。

参考李博杰《深入理解 AI Agent：设计原理与工程实践》§5.1。
