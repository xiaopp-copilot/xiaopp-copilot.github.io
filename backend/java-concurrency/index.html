Java 基础与并发：从对象、多态到锁和并发集合

Java 的三大特性是什么

新大陆面试原题。 封装把状态和操作放进对象，用访问控制保护内部实现。继承让子类复用父类的行为并提供扩展点。public、protected 成员可继承，同包还涉及包可见成员，private 成员不可由子类直接访问，也不作为继承成员。多态允许同一调用因实际对象不同而执行不同实现，例如 Animal a = new Dog(); a.speak();。这里有继承或接口关系，子类型提供自己的实现，调用通过父类型引用完成。静态方法隐藏和实例方法重写要分开，运行时分派讨论的是实例方法。

创建线程有哪些方式

浩鲸科技一面追问。 继承 Thread 并重写 run()，或者实现 Runnable 后传给 Thread，再用 start() 启动线程。需要返回值或声明受检异常时，可以实现 Callable<V>，用 FutureTask<V> 包装后交给线程执行，或直接提交给执行器。Future.get() 在结果未完成时可能阻塞。应用里的批量异步任务通常由线程池统一管理。

JMM、volatile 和 CAS

Java 内存模型定义多线程对共享变量读写时的可见性和顺序。主内存与工作内存是理解共享读写的抽象，判断一个读能看到哪些写时应看 happens-before 关系。典型规则包括同一监视器的解锁先于后续加锁，以及对同一 volatile 变量的写入先于后续读取。

  • 可见性关心一个线程的写入何时能被另一个线程看到。volatile 可用来发布状态，正确使用同一把锁也能建立可见性保证。
  • 有序性关心哪些操作可重排。volatile 对读写周围的操作施加顺序约束，具体屏障由 JVM 和硬件实现。
  • 原子性关心一组操作是否可被并发线程观察到中间状态。volatile int count 的 count++ 仍有读、加、写三步，会发生丢失更新。可用 synchronized、ReentrantLock 或 AtomicInteger.incrementAndGet()。

CAS 比较内存位置的当前值与预期旧值，匹配时原子地写入新值。失败后可读取新值再重试。它常用于乐观并发控制，激烈竞争下反复重试会消耗 CPU。数值经历 A→B→A 时，仅比较值看不出中间变化，这就是 ABA 问题，可按需要用 AtomicStampedReference 加版本标记。

synchronized 能修饰变量吗

深势科技一面。 synchronized 能修饰实例方法、静态方法，也能声明同步代码块。synchronized (lock) 引用的对象是监视器，写法没有给变量本身加修饰符。实例方法锁 this，静态方法锁声明类的 Class 对象，同步代码块允许选择一个共享锁对象并缩短持锁范围。保护同一份状态的所有访问必须遵守同一锁约定。若 A、B 两组状态彼此独立，可用两把锁分别保护。

用 javap -v 看字节码时，同步代码块对应 monitorenter 和 monitorexit，同步方法带 ACC_SYNCHRONIZED 标志。线程正常返回或抛异常离开同步范围时会释放监视器。监视器可重入，已持有它的线程可以再次进入。对象身份用于关联同步状态，HotSpot 的对象头和监视器结构记录或关联锁状态。发生竞争时，有持有者、等待进入的线程和因 wait() 进入等待集合的线程。HotSpot 可以按需膨胀监视器。

旧版 HotSpot 常用无锁、偏向、轻量级和重量级解释优化过程。偏向锁适用于单线程频繁获取同一把锁，轻量级路径可用 CAS 等方式尝试获取，竞争加剧时可膨胀为监视器并挂起等待线程。实现随 JDK 版本调整，JDK 15 已默认禁用偏向锁。OpenJDK JEP 374

ReentrantLock 和 AQS 怎么配合

ReentrantLock 的同步器基于 AQS。state 为 0 时表示未加锁，持有者重复加锁会增加持有计数，exclusiveOwnerThread 跟踪持有线程。获取失败的线程封装成节点进入基于 CLH 的同步队列，等待再次尝试。unlock() 放在 finally，确保异常路径也释放。

默认使用非公平模式，也可以配置按等待顺序竞争的公平模式。lockInterruptibly() 支持可中断等待，tryLock() 支持立即尝试，tryLock(time, unit) 支持限时等待。多个 Condition 可为不同条件维护等待队列。JUC 还提供原子类、线程池和并发集合，Semaphore、CountDownLatch 也基于 AQS 表达各自的同步条件。

sleep 和 wait 有什么区别

对比项 Thread.sleep(...) Object.wait(...)
所属类型 Thread 的静态方法，暂停当前线程 Object 的实例方法，作用于指定监视器
锁 保留已经持有的监视器 释放调用对象的监视器，其余锁保持
调用条件 无需持有监视器 调用线程必须持有该对象的监视器，否则抛出 IllegalMonitorStateException
恢复方式 到期继续调度，或者被中断 同一对象上的 notify()、notifyAll()、超时或中断，也可能虚假唤醒
线程状态 正时长等待是 TIMED_WAITING 无超时等待是 WAITING，带超时则是 TIMED_WAITING

wait() 返回前要重新获取该监视器。条件等待应放在 while 中，每次醒来都重新检查条件。

HashMap、Hashtable 和 ConcurrentHashMap

  • HashMap 适合单线程或已经由调用者同步的使用方式，允许一个 null 键和多个 null 值。默认负载因子为 0.75，元素数超过扩容阈值时通常把桶数组容量翻倍。JDK 8 扩容时可用哈希中的新增容量位决定节点留在原下标还是移到原下标加旧容量。扩容改善桶的分布，减少碰撞和退化风险。
  • Hashtable 的主要操作在同一个对象监视器上同步，键和值均不接受 null，高竞争下写入容易串行化。
  • ConcurrentHashMap 的 JDK 7 实现按 Segment 分段，每个段用 ReentrantLock 管理写入，默认并发级别 16 是构造参数默认值。JDK 8 的实现使用桶数组、链表和红黑树，空桶插入常用 CAS，已有碰撞的桶更新使用桶级同步，并支持多个线程协助扩容。树化还要看表容量，容量较小时会优先尝试扩容。复合更新可用 putIfAbsent、compute 等原子操作。

挖角面试追问，HashMap 为什么线程不安全？ 它没有为并发更新提供同步和可见性保证。两个线程同时写同一个桶或在扩容中继续读写，可能出现更新丢失或读到不一致的状态。可按使用方式选择外部同步或 ConcurrentHashMap。

哈希冲突怎么处理？ 链地址法把碰撞元素放在同一个桶中，HashMap 是例子。开放寻址法在数组里按规则找下一处位置，例如 ThreadLocalMap 的线性探测。再哈希法使用另一哈希函数进一步定位。单进程内并发访问可以用 ConcurrentHashMap，跨节点的会话或缓存见 Redis 与缓存。OpenJDK 并发集合源码
