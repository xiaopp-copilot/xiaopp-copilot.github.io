网络与 Web：TCP、HTTPS、认证和 SSE

TCP 怎么保证可靠，和 UDP 有什么区别

两者都是传输层协议。TCP 面向连接，为应用提供有序字节流。它用序列号定位字节、用 ACK 确认，用超时或丢失检测触发重传，用校验和检测传输损坏。接收窗口用于流量控制，避免压垮接收方，拥塞窗口及慢启动、拥塞避免等机制用于控制网络压力。这些机制保证传输可靠性。机密性和身份认证通常由上层 TLS 提供。

UDP 无需先建立连接，保留数据报边界，协议自身没有交付、排序或重传承诺。应用可以在它之上实现自己的可靠性和拥塞控制。实时音视频等场景常选 UDP，但实际延迟和吞吐还受实现、路径和业务需求影响。

三次握手。 客户端发送 SYN 并进入 SYN_SENT。服务端回复 SYN + ACK，进入 SYN_RCVD。客户端回应 ACK 并进入 ESTABLISHED，服务端收到后也进入 ESTABLISHED。双方借此确认初始序列号和双向通信路径。

HTTP 与 HTTPS，证书怎么验证

HTTP 默认端口 80，HTTPS 默认端口 443。HTTPS 用 TLS 提供机密性、完整性与对端认证。建立 TLS 会话和加解密有额外开销，可以通过连接复用、会话恢复等减少重复握手。

服务端证书将域名或服务身份绑定到公钥。客户端收到证书链后检查签名链是否连到受信任的根、主机名、有效期和用途等，并验证服务端能证明持有对应私钥。证书可以由受信任 CA 免费或付费签发。

什么时候用对称、什么时候用非对称密码？ 以现代 TLS 为例，握手阶段用非对称签名完成常见的证书认证，通过例如 ECDHE 的密钥协商派生会话密钥。记录数据通常用 AES-GCM 或 ChaCha20-Poly1305 等 AEAD 对称算法保护。旧版 TLS 支持用服务端 RSA 公钥传输预主密钥，TLS 1.3 已去除这条路径。TLS 1.3 标准

GET、POST 和请求内容类型

GET 表示读取，一般具备安全和幂等语义，查询条件常写在 URL。POST 表示让目标资源处理提交的数据，常把数据放在请求体，默认不具备幂等语义。应用可以为创建订单等 POST 接口设计幂等键。GET 请求体没有通用语义，URL 和请求体的实际大小都可能受客户端、代理和服务端限制。对敏感数据应使用 HTTPS 并管理日志、缓存和参数位置。GET 响应通常可缓存，POST 响应在满足明确缓存条件时也能缓存。

除了 application/json，常见 Content-Type 有 application/x-www-form-urlencoded（键值表单）、multipart/form-data（多段表单或文件）、text/plain（纯文本），以及 application/xml 或 text/xml（XML）。HTTP 语义标准

Session、Cookie、Redis Token 和 JWT

方式 会话状态和请求凭证
Session + Cookie 登录成功后服务端创建 Session，浏览器 Cookie 携带 SessionID。多实例可用 Redis 共享 Session
Redis Token 服务端生成随机不透明令牌，用令牌作键保存身份或会话信息并设 TTL，便于续期与主动撤销
签名 JWT 常见紧凑格式有 Header、Payload 和 Signature。Header 声明算法和类型，Payload 包含用户标识及过期时间等声明，Signature 用来校验完整性与来源

Cookie 是浏览器保存并发送凭证的载体，可以保存 SessionID，也可以保存 JWT。JavaScript 也可以从内存或浏览器存储取令牌并通过 Authorization: Bearer … 传递。Cookie 要考虑 HttpOnly、Secure、SameSite 和 CSRF，脚本可读的浏览器存储需要考虑 XSS。签名 JWT 的载荷通常可直接解码，服务端验签时还要检查约定的算法、过期时间、签发者和受众。

Access Token 过期怎么续期？ 常用短期 Access Token 加长期 Refresh Token。客户端凭有效刷新令牌申请新访问令牌。刷新流程可使用轮换、失效记录或服务端会话，以支持撤销。Redis 会话可选择滑动 TTL。对于已经签发并包含 exp 的 JWT，延长 Redis TTL 不会改写 JWT 自带的过期时间，需要重新签发。JWT 标准

登录接口如何防暴力破解

面试里可按账号、IP 等维度限流。失败次数达到阈值后增加等待时间或临时限制，结合风控决定是否增加验证码或多因素认证。未知账号和密码错误使用统一提示，减少身份枚举。记录异常尝试并告警，设计限流和锁定时也要避免正常用户轻易被误封。

为什么用 SSE，什么时候用 WebSocket

面试举的是服务端逐段返回生成内容的场景，核心需求是客户端触发一次操作，服务端单向持续输出。我会从四点解释选择：

  1. 可以先展示收到的第一段数据，减少用户等待完整响应的时间。
  2. 浏览器原生 EventSource 支持自动重连。服务端发送事件 ID，并按 Last-Event-ID 实现补发后，才能恢复到合适的位置。
  3. 基于标准 HTTP，响应类型为 text/event-stream，能复用已有代理和认证设施，需要检查代理缓冲、连接超时和心跳。
  4. 单向事件流适合这类请求。需要客户端和服务端持续双向独立发送数据时，可以评估 WebSocket。

普通 HTTP 也可以做流式响应，SSE 提供约定好的事件格式和浏览器接口。原生 EventSource 使用 GET，若提交参数必须用 POST，可以先 POST 创建任务，再通过 GET 订阅，或用 fetch 读取流并自行处理重连和解析。HTML 标准中的 Server-Sent Events
