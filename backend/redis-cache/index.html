Redis 与缓存：数据结构、持久化、分片和分布式锁

商家数据该用什么结构

滴滴一面原题。 先把访问方式拆开。整块读取商家详情可用 String 缓存序列化对象，需要按字段读取或更新时可用 Hash。附近门店可评估 GEO，热度排名用 ZSet，标签去重或交集用 Set。判断依据是怎么读、怎么写、数据量和过期粒度。

类型 场景 底层编码要点
String 对象缓存、Token、计数器、基础锁 可用 int 保存能表示的整数。SDS 短字符串常用 embstr，常见阈值 44 字节，字符串和对象一起分配。长字符串用 raw 分开分配
Hash 商家、用户、角色等对象的字段读写 小对象可用 ziplist，Redis 7.0+ 对应 listpack。扩大后转字典，使用拉链法处理碰撞并支持渐进式 rehash
List 最新动态、简单先进先出队列 早期用 ziplist 或双向链表。Redis 3.2 起使用以双向链表串联紧凑节点的 quicklist，Redis 7 起以 listpack 替代其旧压缩列表节点
Set 去重、共同好友、标签交并集 小整数集合可用 intset，较大集合走哈希表。Redis 7.2+ 还支持适合小集合的 listpack
ZSet 排行榜、按时间戳查找延时任务 小集合使用紧凑编码。大集合用跳表与字典配合，定位和插入通常为 O(log N)，范围结果遍历再加 O(M)，按成员查分数平均 O(1)

Redis 7 常见的紧凑编码门槛是 Hash 512 项、字段名和值 64 字节，ZSet 128 项、成员 64 字节，intset 常见 512 项。编码由版本、实际数据和配置决定，可用 OBJECT ENCODING 验证。Bitmap 在 String 上做位运算，HyperLogLog 用稀疏或稠密表示估计基数，GEO 把经纬度编码为 ZSet 中 52 位整数分值，Stream 用基数树与 listpack 保留消息序列。Redis 内存编码说明

百万级用户排名怎么做？ 按榜单周期维护 ZSet，成员用用户 ID，分数用实际排名值。可用 ZINCRBY 增量更新、ZREVRANK 查单个用户名次、ZREVRANGE 取榜首。Redis 位置从 0 开始，同分排序按成员字典序规则处理。业务需要同名次时，要明确并列规则。分片时，一个大 ZSet 仍属于一个槽，还要按内存、更新与读取压力评估拆榜、分区取 Top N 后合并或预计算。

缓存穿透、击穿和雪崩

  • 穿透是大量请求查不存在的键，可使用短期空值缓存、布隆过滤器，或先校验无效请求。
  • 击穿是热点键过期时并发回源，可用互斥重建，获得锁后再次检查缓存，其余请求等待、重试或在业务允许时读旧值。
  • 雪崩是大量键同时过期或缓存整体不可用，可给 TTL 加随机抖动，并在故障时限流、降级和保护数据库。

本地 Map 和 Redis 怎么选，两级缓存怎么同步

ConcurrentHashMap 的数据只在当前 JVM 中，应用重启后需重新预热。多实例会话若只存在一个进程，请求被负载均衡到其他实例时就找不到。Redis 是独立服务，多个应用可以共享会话、缓存或库存状态，并按配置做持久化。Redis 需要网络访问，因此对读多写少的热点数据也可以用 Caffeine 等作为 L1，Redis 作为 L2。

  1. 短 TTL。 给本地缓存设置短过期时间，例如 3 到 5 秒，适用于接受短时旧值的榜单、浏览量和商品描述。
  2. 广播失效。 更新数据库并提交后，删除旧 Redis 缓存，再通过 Redis Pub/Sub、Kafka 或 RabbitMQ 通知各实例删除本地项。Pub/Sub 离线会漏收，常配合 TTL 兜底。用 MQ 广播时要让每个需要失效的实例都能收到事件。
  3. Canal 与 MQ。 Canal 订阅 MySQL binlog，将已提交的变更变成消息，各应用消费后清理本地或共享缓存。需要处理消费延迟、重复、乱序，以及并发回填旧值的问题。
  4. 统一缓存框架。 JetCache、J2Cache 提供两级缓存的封装，可按版本确认 Redis 或 MQ 通知机制、失效范围和故障语义。

Redis 单机用的是哈希环还是哈希槽

深势科技一面。 单节点的所有读写都到同一实例，单纯主从复制也没有按键分片。以我的「友邻探」项目为例，早期的数据量有限，部署优先考虑运维成本，没有引入按键分片。

Redis Cluster 将键空间划成 16,384 个槽，由主节点负责不同槽。常规路由算 CRC16(key) % 16384，哈希标签可让有关联的键落在同槽。一致性哈希环可用于部分客户端或代理分片，例如早期客户端方案，将节点和键映射到环上，扩缩容时减少重映射。面试里先讲自己实际使用的模式，再说明这两种路由机制。

RDB 和 AOF 怎么选

对比项 RDB AOF
机制 把某一时间点的数据写成压缩快照，如 dump.rdb 追加写操作，重启时从基线和增量日志恢复，支持重写
故障损失 可能丢失最后一次完成快照之后的更新 由 appendfsync always / everysec / no 决定，everysec 一般按约 1 秒的丢失窗口估算
体积和恢复 通常较紧凑，适合备份，加载较快 日志可能较大，回放可能较慢，重写可压缩历史
资源开销 后台快照涉及 fork 和写时复制，内存大时需观察停顿和额外内存 追加和刷盘带来 I/O，重写同样有进程和内存开销

使用 aof-use-rdb-preamble yes 可用 RDB 编码作 AOF 基线，再保留增量。Redis 7 起支持多段 AOF 和清单管理。持久化策略应结合允许的数据损失、恢复时间和备份要求，应用进程重启时仍要区分 Redis 服务是否存活。Redis 持久化文档

Redis 分布式锁、Lua 和 Redisson

基础获取用 SET key owner NX PX ttl，owner 是该次持有者的唯一标识。释放时在 Lua 中原子地比较所有者并删除，防止过期后误删下一位持有者的锁。Lua 脚本的执行不会与其他命令交错，但执行出错前的写入不会因此自动回滚。脚本应短小，声明访问的键，Redis Cluster 中一次脚本访问的多个键需在同槽。另一种常见方案是 ZooKeeper 临时顺序节点，由竞争者按顺序等待。

Redisson 的 RLock 用持有者标识和计数实现可重入，关键更新通过 Lua 完成。未显式传固定 leaseTime 时，可由看门狗续期，常用默认超时为 30 秒，可配置 lockWatchdogTimeout。传入固定租期后，锁到期自动释放，不走该续期机制。业务若无法接受旧持有者在租期过后继续写入，还要用数据库版本或 fencing token 做最终写入校验。Redisson 锁与同步器文档
