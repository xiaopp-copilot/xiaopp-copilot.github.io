JVM 与 GC：堆分代、对象晋升和排障参数

JVM 为什么把堆分代

多数对象生命周期短，熬过多次年轻代回收的对象往往能存活更久。针对这种分布，分代收集器可以频繁回收年轻代，减少扫描整个堆的次数，对老年代用适合高存活率的算法。具体布局、回收阶段和默认值随收集器及 JDK 版本变化。

经典布局有 Eden 和两块 Survivor，初始分配通常发生在 Eden。年轻代回收把 Eden 和当前 Survivor 的存活对象复制到另一块 Survivor，满足条件的对象晋升到老年代，随后两块 Survivor 交换角色。一块接收、一块清空，使存活对象和可用空间保持连续，也省去在唯一 Survivor 中边保留边整理的开销。传统配置常用 Eden、S0、S1 大约 8:1:1 说明这个布局。老年代的回收可涉及标记清除或标记整理。G1 等收集器按区域管理堆，Young GC、Mixed GC 和 Full GC 各有自己的触发条件，Full GC 的范围通常涉及整个堆。 Oracle JVM GC 调优指南

新生代对象过早晋升会发生什么

正常晋升与对象年龄、Survivor 容量和收集器的动态策略有关。在部分收集器和配置中，年龄上限常见为 15。Survivor 容纳不下、大对象分配或突发流量使对象存活到下一轮 GC，都可能加速老年代占用增长。

当老年代很快被填满，收集器可能更早启动并发回收或触发 Full GC，造成 STW 停顿变长、P99 恶化、请求超时和 CPU 使用率升高。若对象一直被集合或缓存持有，可达对象回收不了，最终可能出现 OutOfMemoryError: Java heap space。排查时，先用 GC 日志区分短时晋升、频繁回收和回收后占用持续上涨。怀疑泄漏时，再分析堆转储中的对象保留路径。

Java 的四种引用

引用 回收语义与用法
强引用 Object obj = new Object() 是常见例子。对象保持强可达时会被保留
软引用 对象仅软可达时，收集器可按内存需要清理，曾用于内存敏感缓存
弱引用 收集器发现对象仅弱可达时可清理，常见于 ThreadLocalMap 的键与 WeakHashMap
虚引用 配合 ReferenceQueue 跟踪对象回收阶段，可用于资源清理通知

静态变量在哪里？ JMM 将实例字段、静态字段和数组元素都当作共享变量讨论。问 HotSpot 的具体实现时，静态字段与类对应的镜像对象相关，静态引用指向的普通 Java 对象也在堆上，类元数据则属于另一层概念。在线程池场景中也要区分弱引用键与可能仍被线程强引用的 ThreadLocalMap 值，处理完请求应调用 remove()。

面试问到的常用 JVM 参数

这是按排查目的整理的一组常见选项，参数含义以目标 JDK 和收集器为准。

目的 参数
指定初始堆和最大堆 -Xms、-Xmx
设置单个线程栈大小 -Xss
限制类元数据空间 -XX:MaxMetaspaceSize
选择收集器 如 -XX:+UseG1GC
记录 GC 日志 JDK 9+ 可用 -Xlog:gc*:file=gc.log:time,uptime,level,tags
OOM 时生成堆转储 -XX:+HeapDumpOnOutOfMemoryError、-XX:HeapDumpPath

排查问题时，可以用 jcmd <PID> VM.flags 查看实际 JVM 参数，用 jcmd <PID> GC.heap_info 快速确认堆状态。线程级高 CPU 排查见 Linux 与服务排障。Oracle java 命令参考
